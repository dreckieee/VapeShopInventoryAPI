# 1. Core design decisions

## Stock deduction timing
Stock is deducted from `Product.StockQuantity` at `CloseSale` time, not at `AddSaleItem` time. Built for a single-register, in-person retail context — not designed for multiple simultaneous registers against the same stock pool. Two registers could both add the last unit of a low-stock item to separate open sales before either closes; this is an accepted, documented tradeoff, not an oversight.

## `CancelSale` scope and limitation
`CancelSale` permanently deletes an open sale and any attached `SaleItem` rows, uniformly regardless of item count, since nothing affects stock until `CloseSale` runs. No audit trail is kept for cancelled sales — acceptable since an unclosed sale was never a completed transaction. Once a sale is closed, it cannot be deleted or cancelled through the API by design.

## FK relationships use `Restrict`, not `Cascade`
`SaleItem → Sale`, `SaleItem → Product`, `DeliveryItem → Expense`, `DeliveryItem → Product`, `Settlement → Sale`, and `Settlement → Expense` foreign keys all use `OnDelete(DeleteBehavior.Restrict)` rather than `Cascade`, deliberately. `Cascade` would silently delete child rows whenever a parent is removed — convenient, but it hides deletion behavior inside EF Core's internals rather than making it visible in application code. For a POS system where sale/inventory/delivery/payment audit trails matter, an explicit, visible removal path is safer than an implicit one, even at the cost of extra code.

## DTO construction pattern
Response DTOs (`ProductResponse`, `SaleResponse`, `SaleItemResponse`, `ExpenseResponse`, `DeliveryItemResponse`, `RestockResponse`, and later `CapitalTransactionResponse`, `CashBalanceResponse`, `CashBalanceHistoryEntryResponse`) are `record` types with `init`-only properties, plus a static factory method (`FromX`) for mapping logic (exceptions: `CashBalanceResponse` uses `CreateCashBalance(...)` because it aggregates four independent decimals; `CashBalanceHistoryEntryResponse` is built inline in the walk loop). An earlier private-constructor + `[JsonConstructor]` pattern was reconsidered as over-engineered for flat DTOs with no real invariant to protect — needing `[JsonConstructor]` at all was itself a signal the pattern fought `System.Text.Json`'s natural model. Request DTOs keep public setters, since framework model-binding constructs them externally and they have no invariant to protect.

## Explicit namespace declarations across the Api project (Day 98–99)
All files in the main API project and test project declare explicit namespaces (`VapeShopInventoryAPI.Api` for root files, `VapeShopInventoryAPI.Api.DTOs` for DTOs/, `VapeShopInventoryAPI.Api.Exceptions` for Exceptions/), replacing the previous implicit/global namespace. `Migrations/` files were already namespaced by EF Core codegen. `Program.cs` stays in the global namespace by structural necessity (top-level statements can't carry a namespace declaration) and instead takes a `using VapeShopInventoryAPI.Api;` directive.

## PaymentMethod/PaymentNote wiring and DTO required-field audit (Day 108)
**Enum guard design.** Added `Enum.IsDefined` validation for `PaymentMethod` in both `Sale.GuardSale` and `Expense.GuardExpense`, throwing `ArgumentOutOfRangeException` rather than plain `ArgumentException` — matches .NET's convention for "value outside a defined set" and is still caught by existing `catch (ArgumentException)` blocks, since it's a subclass. The error message is built from `Enum.GetNames<PaymentMethod>()` joined at runtime, so it can't drift if the enum's values change.

**Bug: silent default on omitted/unassigned PaymentMethod.** Two related bugs, same root cause — validating a value without assigning it: (1) `Sale`'s constructor called `GuardSale(saleDate, paymentMethod)` but never assigned `paymentMethod`, so every new `Sale` silently defaulted to `PaymentMethod.Cash` (enum value `0`), indistinguishable from a legitimate `Cash` selection; (2) the same risk exists at the DTO layer: value types (`decimal`, `int`, `DateTime`, `enum`) have non-null defaults, so an omitted JSON field silently binds to that default, which can look like valid data. Fix: the constructor bug was corrected directly (assign after guarding). For the DTO risk, all 10 request DTOs were audited and `required` applied to every field whose default could pass as legitimate input. `required` checks whether the JSON key was present at all, so it distinguishes "explicitly sent 0" from "omitted" even where `0` is meaningful (e.g. `LowStockLevel`). Response DTOs were excluded at the time (later brought under `required` too — Day 135).

**Bug: unhandled exceptions on Create/Update endpoints (500 instead of 400).** `SalesController.CreateSale`, `ExpensesController.CreateExpense`, and `ExpensesController.UpdateExpense` called entity constructors/mutators capable of throwing `ArgumentException`-family exceptions with no try/catch, so a guard failure would have produced a raw `500` instead of the project's standard `400`. Fixed by wrapping all three in `try/catch (ArgumentException ex) → BadRequest`, which also covers `ArgumentNullException` and `ArgumentOutOfRangeException` as subclasses.

**Inconsistency: UpdateExpense returned NoContent.** `UpdateExpense` returned `204` while `SalesController.EditSale` returns `Ok(saleResponse)`. Changed `UpdateExpense` to `Task<ActionResult<ExpenseResponse>>` returning `Ok(response)`.

**Considered and rejected: true partial-update (PATCH).** Partial updates need an `Optional<T>` wrapper or `JsonPatchDocument` to resolve an unavoidable ambiguity — a nullable field like `PaymentNote` can't distinguish "caller omitted this field" from "caller wants to clear it to null", since both deserialize to `null`. Meaningfully more complexity than the need justifies. Full-replacement PUT stays the standing pattern; the "caller has to remember every field" concern is solved at the client layer (a frontend pre-fills the edit form via `GET`, standard REST practice).

# 2. Restock (Day 102)

## Category handling
`Expense`'s existing shape already supported restock with no schema change — it already had a required, non-empty `Category` string. Drift prevention: `Expense.RestockCategory` const ("Restock"), auto-assigned on every restock-generated expense, never user-supplied. This closes the drift risk for the restock path only. The broader problem — `Expense.Category` is free-text everywhere else, so manual categories can drift ("Rent" vs "rent") and silently break filtering — remains open and is queued: replace the free-text field with a `Category` entity + FK, with user-managed CRUD rather than a fixed enum (chosen deliberately for portfolio signal: full relational CRUD + delete-guard pattern).

## Scoping decisions made the same day
Two real operational needs surfaced: (1) real-time cash-on-hand split across payment methods (income reporting can't answer "what's in the drawer right now"); (2) bad products/returns/replacements across three scenarios (supplier defect pre-sale, customer refund, replacement — possibly a different product). Both depend on a `PaymentMethod` field on `Sale`/`Expense`, which didn't exist yet. Receivable/payable tracking stays informal — no `Customer`/`Supplier` entity; a free-text `Party` field was considered for the future ledger, deliberately deferred until per-person tracking is a confirmed need.

## Final design
Moved from "one Expense, no itemization" to a fully itemized batch endpoint:
- `POST /api/restock`, batch shape (`Items: [...]`) — chosen over `/products/{id}/restock`, since a delivery event isn't an action on one existing Product. A single-product restock is a batch of one; no separate single-item endpoint.
- One `Expense` per call (one delivery invoice = one Expense), even across multiple products or the same product at two unit costs.
- Per-product cost tracking was judged important for reviewing past deliveries. A cheaper alternative (auto-generated itemized `Expense.Description` string) was rejected: a formatted string can't be queried or aggregated ("how much did I spend on Product X this year" needs parsing free text), and it broke the codebase principle of not storing structured information as an opaque blob.
- New `DeliveryItem` entity: `ProductId`, `Quantity`, `UnitCost`, computed `TotalCost` (never stored), FK to `Expense` and `Product` (both `Restrict`).
- `DeliveryItem` has no navigation properties (nothing inside it calls behavior on `Product`/`Expense`; orchestration lives in the controller) and no `Edit` method (editing would silently desync `Product.StockQuantity` and `Expense.Amount`, already derived at restock time, without a dedicated reversal/adjustment flow, which doesn't exist yet).
- `RestockRequest.TotalAmount` dropped — `Expense.Amount` is always computed server-side as the sum of `Quantity * UnitCost`, never caller-supplied (same "computed, not independently editable" principle as `Product.IsLowStock`).
- Restock validates every `ProductId` exists (and `Quantity > 0`, `UnitCost >= 0`) before creating anything — all-or-nothing, so a partial failure can never leave a persisted `Expense` that doesn't match what was restocked.

## Build and verification
Built `DeliveryItem`, DbContext registration, migration `AddDeliveryItem`, `RestockController`, and four DTOs (`RestockRequest`, `RestockItemRequest`, `RestockResponse`, `DeliveryItemResponse`). Verified end-to-end via Swagger: single-product restock, multi-product batch, and the duplicate-ProductId-different-unit-cost scenario (both lines itemized, Expense total summed both, stock updated once with the combined quantity). Automated coverage now exists in `RestockApiTests`. `ProductHistory` remains scoped but not built; counter retirement (`ReductionFrequency`/`TotalQuantityReduction` → computed from history) is queued behind it.

## Tooling
`dotnet-ef` updated from 10.0.9 to 10.0.10 via `dotnet tool update --global dotnet-ef`, matching the runtime and resolving a standing cosmetic version-mismatch warning.

## Settlement feature — COMPLETE and DEPLOYED to production as of Day 141 (SettlementCalculator semantics corrected Day 144, fix DEPLOYED to production Day 145)
- One `Settlement` entity (not two separate Sale/Expense settlement entities) — nullable `SaleId`/`ExpenseId`, exactly one set, never both, never neither (constructor-guarded). Fields: `Id`, `SaleId?`, `ExpenseId?`, `Amount`, `PaymentMethod`, `PaymentNote?`, `Date`. FK-only, no navigation properties. Both FKs `Restrict`, not `Cascade`.
- Settlement `PaymentMethod` restricted to `Cash`/`DigitalPayment` only — `Receivable`/`Payable` are invalid values for a settlement itself (guarded in constructor).
- Settlement `Amount` must be `> 0` (constructor-guarded) and must not exceed the target Sale/Expense's outstanding balance (exact-or-under only, no overpayment/credit-balance concept) — this second guard lives at the controller/service layer, not the entity constructor.
- Settlement creation requires the target Sale/Expense's current `PaymentMethod` to be `Receivable`/`Payable` respectively — rejected otherwise via `BadRequest`, checked directly in the controller. Non-existent `SaleId`/`ExpenseId` in the request body returns `400`, not `404` — the URL itself is valid, the invalid reference is in the body.
- Settlement requires the target Sale to be closed (`IsClosed == true`), independent of the Receivable/Payable guard — `IsClosed` and `PaymentMethod` are independent fields on `Sale`. Checked ahead of the `PaymentMethod` check, with its own distinct error message. Only applies to Sale targets; Expenses have no `IsClosed` concept.
- `CreateSettlement` rejects a settlement dated earlier than the Sale/Expense it targets — `sale.SaleDate > request.Date` / `expense.Date > request.Date` (strictly greater than; same-day settlement is valid), returning `400 BadRequest`. A settlement predating the debt it's settling is logically invalid. Checked after the existing IsClosed/Receivable-Payable checks, before the overpayment check, in both the Sale and Expense blocks.
- Settlement is fully immutable — no edit endpoint, no delete endpoint, ever. A mis-recorded settlement is a manual/rare operator-error case, not a feature to build around.
- Once any settlement exists against a Sale or Expense, that record's `PaymentMethod` field is permanently locked — established Day 135, implemented Day 138: guard checks `Settlements.AnyAsync(se => se.SaleId/ExpenseId == record.Id)` AND `request.PaymentMethod != record.PaymentMethod` (comparing against the record's current value, not a hardcoded enum value — this is the correct comparison, not `request.PaymentMethod != Payable`/`Receivable`), returns `409 Conflict` with a distinct message if both true. In `UpdateExpense`, ordered **after** the existing `DeliveryItems`/`Amount`/`Category` guard, and **before** the Amount floor-lock guard — deliberate ordering: the `DeliveryItems` guard represents a broader-scope block (blocks specific fields regardless of what else changes), so it's surfaced first, giving the caller the more consequential piece of information before narrower ones. In `EditSale`, the guard is a plain controller-level `if`/`return` placed before the `try` block — it cannot throw, so it doesn't need the try/catch built for `sale.EditSale(...)`'s exception types.
- **PaymentMethod lock guard test coverage is now fully complete on both `EditSale` and `UpdateExpense` — confirmed Day 141.** Both the `409` conflict path (full-field-unchanged verification, Day 140) and both success-path shapes (same-value edit, no-settlement-exists) are tested for Sale and Expense alike. On Sale specifically, the same-value-edit success path cannot reach `200 OK` — `EditSale` calls `GuardClosedSale()` unconditionally, and a Settlement can only target an already-closed Sale, so there is no reachable state where a settled Sale is still editable at all. That case is instead tested as a `400 BadRequest`, confirming the lock guard doesn't produce a false-positive `409` ahead of the closed-sale rejection. This is a structural fact about the domain, not a test gap — don't attempt to engineer a Sale success path for this guard in the future.
- Once any settlement exists against an Expense, `Amount` cannot be edited below the total already settled (`409 Conflict`) — floor-lock, not a full lock (established Day 139). Decision reasoned explicitly between two options: (A) lock `Amount` entirely once any settlement exists (mirrors Settlement's own immutability), vs. (B) allow `Amount` edits freely as long as the new value stays `>= AlreadySettled` (floor-lock). **(B) was chosen** — a Settlement is the actual payment-transaction record and should stay immutable, but an Expense's `Amount` is a mutable fact about the world (e.g. a misread invoice) that a Settlement merely references. Implemented in `UpdateExpense` by computing `(outstandingBalance, alreadySettled)` via `SettlementCalculator.CalculateExpenseBalanceAsync` up front whenever `hasSettlementReferences` is true, reusing that same query result for both the PaymentMethod-lock check and the Amount floor-lock check. Does not apply to Sales: `EditSale` is already fully blocked once a Sale is closed (`GuardClosedSale()`), and Settlements can only target closed Sales, so there is no window where a Sale has settlements and is still editable at all.
- Once any settlement exists against an Expense, `Date` cannot be edited to a point later than the earliest existing settlement's date (`409 Conflict`) — ceiling-lock, same non-applicable-to-Sale reasoning as the Amount floor-lock guard (`EditSale` is unreachable in a settled state). Implemented by fetching `MIN(Date)` via `MinAsync` scoped **inside** the `hasSettlementReferences` guard block (an un-scoped `MinAsync` throws `InvalidOperationException` on an empty sequence — see the general `MinAsync` learning above), rejecting if `request.Date > minDate` (strictly greater; same-day remains valid, consistent with the `CreateSettlement` guard's boundary). Ordered **after** the Amount floor-lock guard in `UpdateExpense` — narrowest-scope settlement-integrity check goes last, since it only fires under one specific edit direction (moving the date later) rather than blocking a field outright.
- `SaleResponse`/`ExpenseResponse` expose computed (not stored) `AmountSettled` and `OutstandingBalance` fields — established Day 135, implemented Day 138, full test coverage (zero/partial/full settlement cases) COMPLETE Day 139 for both Sale and Expense. `SaleResponse` additionally exposes `TotalAmount` (sourced from `Sale.TotalAmount`), added for consistency with `ExpenseResponse` already having `Amount` visible. Both `FromSale`/`FromExpense` factory signatures accept the precomputed values as parameters rather than computing them internally — consistent with 'no DB access in the entity/DTO layer.' **Values for Cash/DigitalPayment records corrected Day 144, DEPLOYED to production Day 145 — see `SettlementCalculator` entry immediately below.** Wired through all 12 relevant call sites as of Day 138 — **any future audit of `FromX` call sites must explicitly check DTOs that wrap/embed another response DTO internally, e.g. `RestockResponse` wrapping `ExpenseResponse`, not just direct controller calls.** **Test convention established Day 139: computed-field assertions must always be made against a freshly re-fetched (`GET`) response object taken *after* the mutating action (e.g. settlement creation), never against a response object captured *before* that action.**
- **`SettlementCalculator` — static helper class (`VapeShopInventoryAPI.Api` namespace), established Day 138.** Two static async methods, `CalculateSaleBalanceAsync(DbContext, Sale)` and `CalculateExpenseBalanceAsync(DbContext, Expense)`, each returning `(decimal OutstandingBalance, decimal AlreadySettled)`. Deliberately two separate methods, not one method taking nullable `Sale?`/`Expense?` params — eliminates silent-failure/silent-overwrite risk via the type system. This class is the single source of truth for the balance calculation — `CreateSettlement`'s guard, all 12 `FromX` call sites, and the Day 139 `UpdateExpense` Amount floor-lock guard, all route through it. Don't reintroduce inline `SumAsync` balance calculations anywhere; extend this class instead. **Note: the Day 140 date guards (`CreateSettlement` date-validity, `UpdateExpense` date ceiling-lock) intentionally do NOT route through `SettlementCalculator`** — they need `MIN(Date)`, a structurally different aggregate from the sum-based tuple this class returns. Don't force-fit date-based queries into this class; a separate direct query is correct here. **`CashBalanceCalculator`'s Receivables/Payables Join-based query is a second, deliberate exception to routing through `SettlementCalculator` — see Cash Balance section below.**
  - **Semantics corrected Day 144, DEPLOYED to production Day 145: for a `Sale`/`Expense` with `PaymentMethod` of `Cash` or `DigitalPayment`, both methods now short-circuit and return `(0m, fullAmount)` — i.e. `OutstandingBalance = 0`, `AlreadySettled = fullAmount` — WITHOUT querying the `Settlements` table at all.** Prior behavior queried for settlements against every record regardless of PaymentMethod, and for Cash/DigitalPayment records (which structurally can never have a Settlement — Settlement's own constructor only permits targeting Receivable/Payable records) this always returned `(fullAmount, 0)` — i.e. reporting a fully-paid-at-creation record as fully *unpaid*. This was a real semantic bug, not a display nitpick: it misrepresented Cash/Digital Sales and Expenses in every `SaleResponse`/`ExpenseResponse`. Found Day 144 while reviewing real Expense data, verified live against real production data on both Sales and Expenses Day 145. Both more correct (a Cash/Digital record genuinely has nothing outstanding) and cheaper (skips a DB round-trip entirely for the common case) than the prior always-query approach. **Don't reintroduce querying `Settlements` for a Cash/DigitalPayment target — the short-circuit is both a correctness fix and a performance win, not a workaround to be 'cleaned up' later.**
  - **A conditional-DTO alternative (a separate response shape for Cash/Digital records omitting `AmountSettled`/`OutstandingBalance`) was considered and rejected Day 144.** It would force `GetSales`/`GetExpenses` list endpoints to return a heterogeneous array shape (different DTO per row depending on PaymentMethod), breaking typed deserialization (`List<SaleResponse>`) without dropping to untyped/dynamic responses, and would require the variant DTO duplicated for both Sale and Expense. The current approach (always-present fields, computed correctly per PaymentMethod) has a near-zero cost (a couple of always-derivable fields) versus a real, compounding cost from the alternative. Don't revisit this without a genuinely new constraint. **Same reasoning extended Day 145 to Cash Balance History's per-row DTO shape — locked Day 148 as one unified DTO, see the Cash Balance History section.**
- `SumAsync` on an empty sequence returns `0` for a non-nullable `decimal` selector — confirmed safe, no null-handling needed for a target with zero existing settlements. **Contrast with `MinAsync`, which is NOT safe on an empty sequence — see general learning above.**
- Settlement gets its own standalone controller (`SettlementsController`, `POST /api/settlements`, `GET /api/settlements/{id}`) — not nested under Sale/Expense routes.
- **`GET /api/Settlements` list endpoint (year/month filters, matching Expense/Sale list pattern) built Day 142 (Sept 14) — supersedes the prior Day 136 deferral.** The Day 136 note ('no consumer exists yet') no longer applies: a real casual-browse need surfaced (viewing settlements without needing to remember an id). Same query-filter shape as `GetExpenses`/`GetCapitalTransactions`.
- Settlement test fixtures (`SettlementsApiTests`) use `CreateTestSaleAsync`/`CreateTestExpenseAsync` for guard-only tests not touching SaleItems/balance, and `CreateTestSaleWithItemAsync` (produces a closed Sale with a real non-zero `TotalAmount`) for the happy-path Sale test and the overpayment-guard test.
- Settlement test teardown bypasses the API entirely via direct DbContext access — the first entity in this project needing this pattern, since Settlement has no delete endpoint by design. Teardown order: settlements deleted before their target Sale/Expense is cleaned up, or the existing `Restrict`-guard skip on Sale/Expense cleanup will fire and leave the Sale/Expense stranded.
- **Test organization by causal origin, not endpoint ownership, reinforced Day 140–141.** Settlement-related guards on other entities' endpoints (PaymentMethod-lock, Amount floor-lock, Date ceiling-lock, all on `EditSale`/`UpdateExpense`) live in `SettlementsApiTests`, because Settlement's existence is the cause of the guard, not the controller being called. Applied consistently to the Day 141 success-path tests as well. **Same principle applied Day 143: the `CashBalanceCalculator` sanity test lives in its own `CashBalanceCalculatorTests` file, not folded into `SettlementsApiTests`/`CapitalTransactionsApiTests`, because its causal origin is the calculator's formula correctness, not any one entity's endpoint behavior.** **New Cash/DigitalPayment coverage for the Day 144 `SettlementCalculator` fix, by contrast, lives directly in `SalesApiTests`/`ExpensesApiTests`, not `SettlementsApiTests` — because the causal origin is each entity's own PaymentMethod-driven behavior, not Settlement's existence (a Cash/Digital record never has a Settlement at all).** **Same principle applied Day 157: `CashBalanceHistoryApiTests.cs` is its own file, separate from `CashBalanceCalculatorTests.cs` — the history endpoint's causal origin is a structurally different feature (windowed transaction log vs. a point-in-time aggregate), not a variant of the existing Cash Balance tests.**

## CapitalTransaction feature — COMPLETE, fully tested (17/17), DEPLOYED to production as of Day 145
- Built as a prerequisite for Cash Balance: models owner deposits/withdrawals of cash/digital funds into or out of the business, kept fully separate from `Expense` and `Settlement`.
- Using `Expense` for withdrawals was explicitly considered and rejected — `Expense.Amount` feeds `IncomeController`'s revenue query directly; an owner draw is not a business cost and would distort Income/profit figures.
- Naming settled as `CapitalTransaction` after iterating through `CashMovement` → `Equity`/`Capital` → `OwnerTransaction` — `CapitalTransaction` matches the standard accounting term for owner contributions/draws while staying unambiguous about being a transaction *record*, not a stored balance (an entity named `Equity`/`Capital` alone would misleadingly read as a balance).
- `Type` enum is `CapitalTransactionType { Deposit, Withdrawal }` — everyday terms chosen deliberately over the accounting terms `Contribution`/`Draw`.
- Fields: `Id`, `Type`, `Amount`, `PaymentMethod`, `Note?`, `Date`, `CreatedAt`. `CreatedAt` is an intentional field on this entity — confirmed to exist on other entities in this project already, not a new one-off pattern.
- Constructor guards: `Amount > 0`; `Type` must be a defined enum value (`Enum.IsDefined`, else `ArgumentOutOfRangeException`); `PaymentMethod` must be a defined enum value (`Enum.IsDefined`, else `ArgumentOutOfRangeException`) AND must not be `Receivable`/`Payable` (else `ArgumentException`) — mirrors `Settlement`'s guard shape exactly, both checks required (an `Enum.IsDefined`-only check would let `Receivable`/`Payable` through since they're valid enum values; an `== Receivable || == Payable`-only check would let a genuinely undefined enum value through); `Date` cannot be `default` (distinct message) and cannot be later than `DateTime.Now` (distinct message — these two date failures must not share the same exception message, since they represent different violated rules).
- No navigation properties — `CapitalTransaction` targets no other entity, so the FK-only pattern doesn't even apply here; there's nothing to reference.
- Fully immutable — no `Edit` method, no edit endpoint, no delete endpoint, ever, same rationale as `Settlement` (a real-world financial event, not a correctable business record).
- DTOs: `CreateCapitalTransactionRequest` (class, public set, `Type`/`Amount`/`PaymentMethod`/`Date` all `required`, `Note` nullable/optional — not required); `CapitalTransactionResponse` (record, init-only, every field `required` including nullable `Note`, `FromCapitalTransaction` factory, no DB access inside).
- Controller: standalone `CapitalTransactionsController` (not nested under any other entity's routes) — `POST /api/CapitalTransactions`, `GET /api/CapitalTransactions/{id}`, `GET /api/CapitalTransactions` (list, `?year=`/`?month=` filters, same shape as `GetExpenses`/`GetSettlements`).
- Migration `AddCapitalTransaction` generated and committed as a single fileset (migration + Designer.cs + ModelSnapshot.cs) Day 142. **Applied to local dev DB Day 144 (was showing `(Pending)` until then) and to production Day 145** — production deploy discovered a transitive dependency: `CashBalanceCalculator` queries `CapitalTransactions`, so deploying Cash Balance without this migration applied first caused a production `500`. Both local and production are now genuinely applied and confirmed clean.
- **Full automated test coverage COMPLETE Day 143 — 17 tests, `CapitalTransactionsApiTests.cs`, one commit per test:** Create valid (Deposit, Withdrawal); Create invalid guards (negative Amount, zero Amount, Receivable PaymentMethod, Payable PaymentMethod, undefined PaymentMethod, undefined Type, default Date, future Date — 8 total); Get (existing id, non-existent id); List filters (year, month, year+month, no-match, no-filter — 5 total).

## Cash Balance feature — COMPLETE, fully tested, DEPLOYED to production as of Day 145
- 4 buckets: `CashOnHand`, `DigitalBalance`, `ReceivablesOutstanding`, `PayablesOutstanding`.
- `CashOnHand`/`DigitalBalance` formula (same shape, swap `Cash`/`DigitalPayment`) — includes `CapitalTransaction` (extended Day 142): + sum of `TotalAmount` for closed Sales of that PaymentMethod, − sum of `Amount` for Expenses of that PaymentMethod, + sum of `Amount` for Settlements of that PaymentMethod targeting a Sale (`SaleId != null`), − sum of `Amount` for Settlements of that PaymentMethod targeting an Expense (`ExpenseId != null`), + sum of `Amount` for CapitalTransactions of that PaymentMethod where `Type == Deposit`, − sum of `Amount` for CapitalTransactions of that PaymentMethod where `Type == Withdrawal`. A Settlement's own `PaymentMethod` (always `Cash`/`DigitalPayment` per its constructor guard) determines which of these two buckets it affects — not the target Sale/Expense's original `PaymentMethod`. Same logic applies to `CapitalTransaction`'s own `PaymentMethod`.
- **Implementation refactored Day 144: Cash and Digital bucket logic (previously two near-duplicate inline blocks in the public method) collapsed into one shared `private static async Task<decimal> CalculateCashOrDigitalBalanceAsync(VapeShopInventoryDbContext context, PaymentMethod paymentMethod)` helper, called twice from the public method with `PaymentMethod.Cash` and `PaymentMethod.DigitalPayment` respectively.** Receivables/Payables logic deliberately NOT folded into a shared helper alongside this — they query different entity types (`Sales` vs `Expenses`, `SaleId` vs `ExpenseId`), so forcing them into one generic method (e.g. via reflection or a shared base type) would add complexity without a real duplication problem to solve. This was explicitly stress-tested Day 144: a '4 separate public methods' alternative was also considered and rejected (see below).
- `ReceivablesOutstanding`/`PayablesOutstanding` formula: sum of `OutstandingBalance` across all Receivable Sales / Payable Expenses respectively. Unaffected by `CapitalTransaction` — deposits/withdrawals have no Receivable/Payable concept. Receivables total (before settlement subtraction) filters `IsClosed`, same as the Cash/Digital Sales sums — confirmed Day 143 as the correct, consistent behavior (an open Receivable sale isn't a finalized transaction and shouldn't count as outstanding revenue). **Findability of individual Receivable/Payable records (rather than their totals) is solved separately by the Day 145 `paymentMethod` filter on `GetSales`/`GetExpenses`.**
- Single `GET /api/cashbalance` endpoint, cumulative/all-time by default — no year/month filter, matching the existing Income endpoint precedent (a balance is a running total, not a period-scoped figure). This endpoint stays a cheap aggregate query regardless of table size (SUM operations execute server-side in the DB, response cost does not scale with row count) — do not add a required date-range param to this endpoint; that requirement belongs to Cash Balance History only. This 'cheap server-side aggregate' property depends on avoiding the `TotalAmount` computed-property translation trap. All Sales-based sums must use `.SelectMany(s => s.SaleItems).SumAsync(...)`, never `SumAsync(s => s.TotalAmount)`, to actually stay server-side. **Confirmed via `CashBalanceController`'s built implementation Day 144 — an early draft of the controller had unused `[FromQuery] int? year, int? month` parameters, caught in review and removed, since accepting-but-ignoring these params would have silently misled a caller into thinking date filtering worked.**
- `ReceivablesOutstanding`/`PayablesOutstanding` computed via a `Join` between `Settlements` (filtered `SaleId != null` / `ExpenseId != null`) and `Sales`/`Expenses` (filtered to `Receivable`/`Payable` respectively), on `SaleId == Sale.Id` / `ExpenseId == Expense.Id`, summing the matched settlements' `Amount` — NOT by looping every Receivable/Payable record through `SettlementCalculator` (deliberate deviation, reasoned as a genuinely different problem shape: an aggregate report needing one final total is not the same as a list endpoint where each individual record's own balance is the point). This is deliberately independent of the Cash/Digital bucket's own settlement sums (which filter by the *settlement's own* PaymentMethod, not by the *target's* PaymentMethod) — don't reuse Cash/Digital bucket intermediates for the Receivables/Payables calculation, even if the numbers happen to match.
- **`CashBalanceResponse` DTO — built and committed Day 144:** record, init-only, four `required decimal` properties (`CashOnHand`, `DigitalBalance`, `ReceivablesOutstanding`, `PayablesOutstanding`), no `Year`/`Month` fields (cumulative-only, unlike `IncomeResponse`'s nullable pattern). Factory method named `CreateCashBalance(...)`, not `FromX` — deliberate exception to the `FromX` naming convention, since this DTO has no single source entity to name the factory after (it aggregates four independently-computed decimals, unlike every other response DTO which maps from one entity).
  - **`DigitalBalance` naming (not `DigitalCash`) — stress-tested and confirmed Day 144, after being raised as a genuine challenge to a Day 143 approved decision, not a re-litigation for its own sake.** `DigitalCash` was rejected: it contradicts this project's own `PaymentMethod` enum, which names the non-cash digital value `DigitalPayment` (not `DigitalCash`) — putting the word 'Cash' on the one PaymentMethod value that explicitly isn't Cash is an internal naming contradiction. `DigitalCash` also collides with an external, unrelated fintech term (CBDC/e-cash/crypto), which `DigitalBalance` does not. The originally-raised ambiguity concern (confusion with Receivables/Payables settled via digital payment) does not hold up: neither `ReceivablesOutstanding` nor `PayablesOutstanding` uses the word 'Balance' anywhere in this DTO, so there's no actual naming collision within the response shape. `DigitalBalance` is used consistently in the tuple (`CashBalanceCalculator`), the DTO, and the controller.

# 4. Known issues and postmortems

## Fixed: orphaned `SaleItem` rows on quantity-reduce-to-zero (Day 92)
`Sale.ReduceSaleItemQuantity` removes a `SaleItem` from its in-memory collection once its quantity reaches zero. Because the `SaleItem → Sale` FK is `Restrict` and required, EF Core had no valid action for an entity severed from its parent's tracked collection — it threw `DbUpdateException` on save. Fixed by explicitly calling `_context.SaleItems.Remove(saleItem)` before saving whenever the domain call removes an item. Covered by a regression test.

## Fixed: `DeleteProduct` had no guard against existing sale records (Day 92)
Previously attempted deletion unconditionally, producing a bare `500` whenever a product had any `SaleItem` reference. Fixed with an explicit existence check returning `409 Conflict` with a clear message, plus a fallback catch for unexpected constraint failures.

## Fixed: `DeleteExpense` had no guard against `DeliveryItem` references (found Day 102, fixed by Day 109)
Deleting an `Expense` that still had `DeliveryItem` rows (e.g. a Restock-category expense) would hit the `Restrict` constraint and surface a raw `DbUpdateException`. The same guard as `DeleteProduct` was applied (now also checks `Settlement` references). Confirmed fixed while reviewing the controller Day 109 (a stale note had continued describing it as an open gap).

## Fixed: environment-specific DB path mismatch (Day 94)
After deployment, `GET /api/Products` returned `500` with `SQLite Error 1: 'no such table: Products'`. Root cause: the connection string used a relative path (`Data Source=vapeshop.db`), EF migrations were run from the repo folder while the systemd service's working directory was different — two folders, two different (initially empty) database files. Fixed immediately by copying the migrated `.db` to the service's working directory, then permanently by adding `appsettings.Production.json` with an absolute path override, so it can't recur regardless of where migrations run.

## Fixed: `GetSales` list missing `.Include(s => s.SaleItems)` (Day 138)
Once `Sale.TotalAmount` became a computed property, every sale in the `GetSales` list response would have silently shown `TotalAmount = 0` despite having real items (an un-included navigation collection is an empty list, not null and not an exception). Fixed as its own isolated `fix:` commit ahead of the `AmountSettled`/`OutstandingBalance` DTO work. Standing rule: any action returning a `SaleResponse` uses `.Include(s => s.SaleItems)`.

## Fixed: `SettlementCalculator` reported Cash/Digital records as unpaid (Day 144, deployed Day 145)
See the Settlement section above for full detail. Found by reviewing real Expense data and pushing on an oddity rather than accepting it, despite the decision being 'locked'.

## Fixed: production `500` on `GET /api/cashbalance` — transitive migration dependency (Day 145)
`CashBalanceCalculator` queries the `CapitalTransactions` table, so deploying Cash Balance without first applying the `AddCapitalTransaction` migration produced `no such table: CapitalTransactions` even though Cash Balance's own code has no schema change. Fixed same-session by applying the migration (no republish needed). Lesson: before treating two features as independently deployable, check whether either one's code paths reference a table the other one's migration creates.

## Corrected: `SaleDate`/`Expense.Date` do carry a time of day (Day 156)
A Day 149 conclusion ('no time of day') was wrong for real data: a production Sale checked live in Swagger showed `saleDate: 2026-07-26T05:15:56.636`. # 5. Testing approach
